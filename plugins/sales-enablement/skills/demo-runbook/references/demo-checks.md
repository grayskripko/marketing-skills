# Demo checks

A demo earns attention when it opens with the result the buyer is after and shows only what serves it (the outcome-first approach in Cohan, Great Demo!, 2nd ed., 2005). These checks turn that into rows a plan or script either passes or fixes.

## Pain ledger

One row per pain the buyer stated: id (P1, P2…), the buyer's words quoted, source (note line or timestamp), the buyer's own number if any, otherwise [METRIC]. A pain the seller inferred is marked "inferred, confirm in the call".

## Scene table

| Scene | Pain | Capability shown | Proof slot | Minutes |
|---|---|---|---|---|

- One scene per pain: each scene answers one pain id and each pain gets one scene. A second capability that serves the same pain becomes that scene's proof slot or goes on the don't-show list. Two scenes on one pain only when the user asks, and the table says so.
- Proof slot: a case, figure or reference from the user's material, otherwise [PROOF NEEDED].
- Minutes are the user's estimate or a default of 6 per scene (you can change it).

## Opening and check-ins

- Opening: the result the buyer wants, in their words, plus the agenda; ask whether the order fits.
- Before each scene: a pain-confirm question ("You said first replies take 9 hours; where does that stand today?").
- After each scene: a compare-with-today question ("How does that compare with how your team handles it now?").
- At the end: what mattered most to the buyer, which also tells the seller what to lead with next time (a default of this plugin).

Closed check-ins to flag in a script: "does that make sense?", "any questions?", "make sense?", "is that clear?", "can you see my screen?" used as a check-in, "does that look good?", "pretty cool, right?". They invite a yes and tell the seller nothing.

## Don't-show list

Every capability the user listed that answers no pain in the ledger. Each gets one line: "hold back unless the buyer asks".

## Discovery gaps

For each of budget, how the decision is made, timeline, current way of working, trigger: known (with source) or unknown. Unknowns become opening questions, at most three.

## PASS / FIX checks

| Check | Rule | Basis | Status |
|---|---|---|---|
| D-1 Pain coverage | every scene maps to one pain in the ledger, one scene per pain | Cohan | PASS / FIX |
| D-2 Scene count | at most 4 scenes | default | PASS / FIX |
| D-3 Time | scene minutes ≤ two thirds of the slot, and the whole running order (opening, questions, scenes, close) ≤ the slot, both compared before rounding | default; leaves time for the buyer | PASS / FIX |
| D-4 Check-ins | no closed check-in phrase | default | PASS / FIX |
| D-5 Proof | every outcome claim has a proof slot filled or flagged [PROOF NEEDED] | ground rule 3 | PASS / FIX |
| D-6 Next step | the plan or script closes by asking for a next step with date and owner; in a plan written before the call, a question that uses the user's date and owner or asks the buyer for them meets this | rubric CS-D08 | PASS / FIX |

Each FIX names the scene or line and the change.

Worked example: 30-minute slot, so the time limit is 30 × 2 ÷ 3 = 20 minutes; two pains, two scenes of 6 minutes = 12 ≤ 20, PASS. Five scenes of 8 minutes = 40 > 20, FIX, and 5 > 4 scenes, FIX.
