## Decide the mapping

1. Identify the objects, create/update intent, file structure, and supplied coverage. Map every header to an object property, identifier, association label, shared join column, or Don't import column. A company name property on a contact is not proof that a company record or association will be created. Keep Record ID columns separate per object.
2. For creation: contacts need Email; companies need Name or Company domain name; deals need Deal name, Pipeline, Deal stage; tickets need Ticket name, Pipeline, Ticket status. Deal stage must belong to its pipeline. Updates require a supported identifier instead of guessing from names: Record ID, contact Email, company Company domain name, or an existing property that requires unique values. An external ID header alone is not evidence of uniqueness in HubSpot. A mapped Record ID supersedes other identifiers; an invalid ID cannot be rescued by Email or domain. A blank mapped ID takes the create path when creation is allowed, or is ignored in update-only mode; flag conflicts with existing emails/domains before import. Verify IDs belong to the object and destination account. A secondary contact email mapped as Email alongside Record ID can replace the primary email. To preserve the primary email, exclude the unintended Email update while retaining a verified ID; do not universally remove Record ID.
3. Check .csv/.xls/.xlsx, one sheet, a header row, fewer than 1,000 columns, and UTF-8 for non-English characters. Free tools: 20 MB/file, 50 imports and 500,000 rows per rolling 24 hours. Smart CRM or Starter/Professional/Enterprise: 512 MB/file, 500 imports and 10,000,000 rows per rolling 24 hours; 1,048,576 rows/file. Both allow three simultaneous imports, at most two over 10,000 rows. Do not assume a paid tier; a text sample cannot establish encoding or size. The API's larger allowance does not apply here. When removing excluded columns, remeasure the corrected file before requiring a split; splitting does not resolve a rolling row allowance.
4. For values: enumeration labels or internal values must exist; default HubSpot enumerations use English labels or internal values. Multiple checkboxes use `a;b`; a leading `;a;b` appends instead of replacing. Dates need an explicit consistent date order; confirm the chosen import date format and time zone. Flag ambiguous dates rather than choosing a locale. Percentages use `25%` or `.25` for 25%; do not silently reinterpret `25`. Single checkboxes accept True/Yes and False/No. Domain paths are stripped by HubSpot; show the proposed domain rather than silently normalizing conflicting identities. Blank cells preserve existing values, not clear them.
5. For single-file associations, each row needs identifiers for the imported objects. Repeat a contact with a different company identifier for multiple associations; do not deduplicate these rows away. For two files, choose a shared join column, check that the referenced side's key is unambiguous, and keep join keys distinct from the identifier used to update CRM records. Resolve unambiguous source keys to verified destination IDs before constructing the handoff; a source-only key is not a HubSpot unique-value property. When suitable, use the associated object’s verified Record ID as the common column. Provide the safe subset while holding ambiguous links; do not block unrelated resolved relationships. Custom labels must already exist and require Professional/Enterprise; use Primary for a primary company association only when that label option is available in the importer. Verify availability on Free/Starter rather than assuming it; the import article states the label tier restriction more broadly than the format article. In two-file imports, put Association label in the same file as the associated object's unique identifier; choose placement from the corrected file layout, not the original filenames. It can stay in the contacts file when that file also carries the associated Company Record ID. Cross-object paired labels need only one label from the pair. Same-object imports require at least one existing record per pair and primary emails/domains, not secondary ones. For same-object paired labels, the Associated [unique identifier] side receives the supplied label and the other side receives its inverse. Imported labels add to existing labels; they do not replace them. If replacement is requested, give the separate manual action to edit labels on that specific association and remove only the named old label while retaining the relationship and other labels. Do not choose Dissociate; do not recommend removal otherwise.
6. Missing unique identifiers usually create duplicate risk. A narrow exception: single-file multi-object Create and update can combine identical object data across rows without an identifier; differing object properties produce separate records. Do not generalize this to single-object or create-only/update-only imports. Never promise that a deal name alone matches an existing deal.

When a manual handoff is requested or needed to resolve a blocker, include the relevant settings: objects; create/update mode per object; identifiers; date/number format; association joins/labels; columns to exclude. Do not assume marketing-contact status or enrichment. If asked to import contacts, flag the consent attestation against purchased lists without inventing permission. Existing-record effects belong in a separate forecast when requested.

## Worked example

Fictional Cedar Vale Instruments provides two rows with columns `Contact email`, `Business domain`, and `Relationship`; the same contact appears with two different domains and the labels Buyer and Adviser. Map the first two columns to contact Email and company Company domain name, and Relationship to Association label. Keep both association rows. Before labeling, verify Buyer and Adviser already exist and the account has Professional/Enterprise. With no export, make no claim that either company is new. Return the mapping and these two label prerequisites, not a fabricated import total.
