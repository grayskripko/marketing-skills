## Native RSS facts that decide the result
Pinterest supports XML RSS 2.* and RSS 1.* (RDF), not Atom. Every item needs an article link under the user's claimed domain. Do not substitute an unrelated destination or assume a subdomain/subpath is covered without the supplied claim scope.
Images are taken from item-level `<image>`, `<enclosure>` and `<media:content>`; titles and descriptions come from item-level `<title>` and `<description>`. A channel logo is not an item image. Pinterest also says it can create Pins for multiple images in an item or webpage: absence of an item image is a repair opportunity, not proof that webpage discovery will fail. Do not impose an undocumented image dimension, byte limit, title limit or GUID requirement on native RSS.
Feed updates may take up to 24 hours according to RSS Help. Pinterest Create describes 24–48 hours when setting up RSS; for a new connection, distinguish that setup window from subsequent updates and do not promise a hard deadline. Oldest feed content publishes first. The documented ceiling is up to 200 Pins per day, not 200 articles. Multiple images can yield multiple Pins. Do not promise queue completion, backfill of content no longer in the feed, or republication after editing an old item. Feed count is unrestricted when feeds match the claimed website; each can target a different board. Secret-board publishing prevents public discovery; the owner can inspect their own board to distinguish hidden Pins from missing Pins.
Describe this desktop path for the user to perform in their own interface: business account → Settings → Create Pins in bulk → Auto-publish → Connect RSS feed → feed URL → Save Pins to (board) → Save. Explain that the user's final Save activates publishing; instruct them to stop before Save if they are not ready. Do not execute the connection or publishing actions yourself. Connect RSS feed appears only with a claimed website; mobile cannot connect it.
Error meanings: “RSS feed already exists” means keep the existing connection if that is the intended feed; use a different feed only to add another; “RSS feed cannot be fetched” means check public URL access; “RSS feed cannot be parsed” means check valid XML RSS; “RSS feed unknown format” means check supported RSS version; “Links in the RSS feed are not under the claimed domain” means check all item destinations against the claim.
Use native publishing only. Do not recommend duplicate-content flooding, redirects to evade domain or spam checks, or unauthorized automation. These boundaries come from Pinterest Community Guidelines, not a diagnosis of an unexplained failure.

## Diagnose and repair
Use this skill for feed content, item fields or an exact feed error. For a request also asking setup, include the relevant native setup actions here; do not force a second skill call.
Lead with the deciding whole-feed blocker, next action, or exact corrected XML fragment. Use an item table for multiple item findings by default, or for a single item when requested or useful; include supplied identifier/title, observed defect, and smallest fix, adding uncertainty only when it changes the repair. Separate whole-feed blockers from item defects and account/timing checks. Preserve supplied values by default, including an ineligible destination in a syntax-only repair. For an operational repair, apply an explicitly supplied or approved replacement within the requested scope and explain the change. If the replacement is unknown, retain the original in a clearly labeled syntax-only artifact or use a specific missing-detail marker in an incomplete proposed repair; identify the remaining destination blocker. Do not manufacture a replacement article or image URL; use a specific missing-detail marker.
Identify root format before item checks. If a full document and a safe local XML parser are available, parse without external entity/network resolution. Claim parsing success only after actually running that parser on the exact document; inspection alone is not a completed test. For conversion, preserve identifiers and modification timestamps without inventing publication dates. If only fragments or screenshot descriptions are supplied, diagnose visible defects without claiming parser success. Check escaping, closing tags and namespace bindings as XML mechanics. Atom needs a supported RSS export, not merely a renamed root.
Resolve deciding whole-feed format, parse or hosting blockers first. For an exhaustive item audit, inspect every relevant supplied item for destination, image fields, title and description; use a safe local parser when available for a complete large document and summarize repeated defects with counts and representative examples. For a targeted diagnosis, inspect affected items and relevant contrasts. State inspected scope, never infer whole-feed validity from a sample, and request complete input or batches when an exhaustive conclusion requires them. In an item-by-item repair list, say what to keep as well as what to change. For RSS 1.0, retain the supplied `rdf:about` identifiers rather than adding RSS 2.0 GUIDs. If dimensions are disputed, calculate the supplied aspect ratio without treating a preferred size as an ingestion requirement. Check omitted RSS 1.0 structure conditionally using the reference; do not call it missing from excerpts. Avoid treating an empty optional field as a documented fatal rejection. Contrast claimed scope with literal destinations; redirects are a possible access/domain issue only when observed. For fetch failures distinguish authentication, HTML instead of XML, denial, redirect and response failures using actual evidence; a pasted document cannot prove hosting works.
When asked what still blocks a repaired feed, answer that question directly: compare all destinations with the supplied claim scope and address any concern about record count (Pinterest lists no minimum). Preserve fictional or anonymized URLs; discuss replacing them only if the user intends to host those literal placeholders. Include native setup steps only when requested or when supplied evidence identifies a setup blocker. For a combined diagnosis/setup request, cover only the remaining actions relevant to the supplied business account, claim, feed, desktop settings, board and timing; use a checklist only when it helps or was requested. If claiming is missing, guide HTML tag in head, verification file in root, or DNS TXT copied within the user's own interfaces; TXT propagation may take up to 72 hours. A website may belong to only one Pinterest claim account. Ask for exact claim scope or error only when it changes a fix.
