# Calculate current-stage aging

Lead with the requested follow-up priority, ages or comparison from pasted rows or selected exports; use a ranked opportunity table when useful. For count reconciliation choose weekly-pipeline-reconcile; this skill contains all rules needed for its own aging result.

## Establish the clock and population

Use the supplied as-of timestamp and timezone, stage/posting scope, opportunity-owner scope, archive policy and confidentiality. If capture predates the cutoff, report ages conditional on the captured stage still being current; label membership, archive and owner state as of capture. Do not claim current active membership without later state evidence. If as-of time is missing, ask for it after showing usable timestamp exceptions; do not silently use the current clock. Default calculation convention for this skill: elapsed 24-hour days, with displayed precision stated. Switch to calendar or business days when the user requests that convention; business days also need the applicable workweek and holiday calendar. These conventions are analysis choices, not Lever-defined SLAs.

## Lever rules that decide the result

If the user restricts evidence to the pasted capture, use only its rows and metadata: do not import API defaults or dashboard definitions, even when Lever is identified. Otherwise apply Lever-specific definitions only when the user or export metadata identifies Lever. For unlabeled tables, use the supplied headers/settings without adding platform attribution; ask for the source only if it decides an unresolved comparison. Do not add documentation links for arithmetic or schema facts already supplied.

- Opportunity `id` and person `contact` are separate keys. Keep multiple opportunities for the same contact. For expanded stage/owner/contact objects, extract IDs. Deduplicate exact repeat opportunity rows; conflicting duplicates are unresolved unless version evidence selects a row.
- `stage` is the current stage ID; the documented Lever API defines `lastAdvancedAt` as entry into that current stage. For a transformed or undocumented export, confirm that mapping if it decides the result; label ages conditional on it until established. Do not replace it with opportunity `createdAt`, `updatedAt`, `lastInteractionAt` or an earlier visit to the same stage. Stage events use `toStageId` and event `updatedAt`; the event timestamp differs from the opportunity's general update timestamp. API timestamps are Unix milliseconds; pasted ISO timestamps must retain timezone. Confirm units for ambiguous numeric exports instead of guessing.
- If the entry field is missing, complete ordered `stageChanges` may establish the latest entry into the current uninterrupted stay. Check stage IDs, later departures, tied events and cutoff. If no event establishes entry into the current stay, age is unknown; do not substitute creation time. If history contradicts `lastAdvancedAt`, mark the discrepancy rather than silently selecting the oldest visit. Partial history is insufficient to reconstruct an arbitrary past cutoff. A current snapshot captured after the requested cutoff needs a corresponding earlier snapshot/history before reporting past ages.
- The API describes archive status as `archived` with `archivedAt` and `reason`; exports/examples may flatten those fields. Explicit null, missing and conflicting values differ. Exclude confirmed archived opportunities from active aging; keep unknown archive states outside the confirmed active denominator. Archive reasons can include Hired; age alone is never a reason to archive someone.
- API opportunity lists include both archive states if `archived` is omitted and non-confidential data if `confidentiality` is omitted. `hasNext`/`next` imply remaining pages; average ages from supplied rows must be labeled for that subset. A 403 or missing confidential permission leaves coverage unknown, not zero.
- Opportunity owner is distinct from posting owner, hiring manager and follower. Preserve missing owners as unassigned/unknown and apply only the supplied owner scope. Signed-in-user Recruiter Operations **Current Operations** differs from **Current Operations - Team View**. Confidential-posting data is excluded from charts. **Performance > Average Time in Stage for Archived Opportunities** measures historical stage time for the owner's opportunities archived in the selected period, not current-stage age for active rows. Stage versus milestone grouping also changes the comparison.
- `advanced_at` filters select entry into the current stage, not every historic stage event. `updated_at` filters do not match the returned `updatedAt` field. Never infer a current-stage age from an update-date export window. For Current Operations > Average Time in Stage for Active Opportunities, prose says stage days but the secondary dataset says pipeline days; Team View's same-named chart lists stage days. Neither specifies repeat-visit handling. Establish the page and exported metric before claiming equivalence.

## Calculate and report

1. Keep valid in-scope opportunity IDs and entry timestamps. Put rows missing opportunity IDs in an identity-exception list with original row references; show their excluded-row count. A valid timestamp can support an unidentified row age, but not distinct-opportunity totals or verified opportunity averages until stable identity and deduplication are established. Separate missing, invalid, future and conflicting times. Unknown age is not zero. Keep those exceptions visible rather than rounding them into the mean.
2. Calculate elapsed days = (as-of Unix milliseconds - entry Unix milliseconds) / 86,400,000. Equivalently subtract timezone-aware ISO timestamps and divide seconds by 86,400. State the shared cutoff and, when explaining ages or aggregates, show the formula once; each row's entry timestamp supplies its other input. Repeat individual substitutions only for requested audit detail or an exception. Use unrounded values for comparisons and aggregates; round only display values.
3. Rank calculable ages descending. Apply only the supplied threshold, preserving its exact operator (> versus >=). Without a threshold, rank ages without declaring an SLA breach.
4. Calculate averages and shares only when requested. Do not add population arithmetic to a simple follow-up list unless missing coverage changes its use. Mean known age = sum of calculable in-scope ages / number of calculable opportunities. Name the eligible population, known denominator and exception count. For no valid ages, mean is undefined. When overdue percentage is requested and ages are unresolved, give both confirmed overdue / calculable opportunities and confirmed overdue / all confirmed active in-scope opportunities. Label the latter a confirmed minimum, not the final overdue rate; include bounds only when useful or requested.
5. Group by stage/owner only when requested or helpful; preserve supplied mappings. Separate stage ages from total pipeline duration and historical stage durations. Suggest the exact data repair for exceptions. For a historical cutoff, first request a complete snapshot certified for that cutoff and scope, with opportunity ID and current-stage entry timestamp (or confirmed `lastAdvancedAt` mapping). Certified scope can replace repeated owner/stage/archive columns. For a chart mismatch, first request its effective time and exact duration definition; request underlying rows only if those leave the comparison unresolved.

Return the ages/overdue rows first and brief exceptions afterward. Use one compact table for known and unresolved active ages where useful. Do not repeat the same evidence in several sections. When a Lever chart or field definition decides a comparison, link its official source next to the finding; dates remain in references. Read [lever-rules.md](references/lever-rules.md) when source detail or an API capture error affects the result.

## Worked example

Copper Finch Research asks for active opportunities as of 2026-10-08T09:00:00Z, elapsed days, threshold >=5, plus the mean known age and overdue share among calculable rows. Opportunity z1/person h1 entered Interview on Oct 2 at 09:00Z; z2/person h1 entered Screen on Oct 6 at 21:00Z; z3 is archived; z4 is active with no entry timestamp.

| Opportunity | Entry (UTC) | Age calculation | Flag |
|---|---|---|---|
| z1 | Oct 2 09:00 | (Oct 8 09:00 - Oct 2 09:00) / 24 hours = 6 days | >=5 |
| z2 | Oct 6 21:00 | (Oct 8 09:00 - Oct 6 21:00) / 24 hours = 1.5 days | below 5 |

Mean known age = (6 + 1.5) / 2 = 3.75 days, over two calculable opportunities out of three active. z4 needs the current-stage entry timestamp; z3 is excluded. Both h1 candidacies remain. Confirmed overdue share among calculable rows = 1 / 2 = 50%; it is not the share of all active opportunities.
