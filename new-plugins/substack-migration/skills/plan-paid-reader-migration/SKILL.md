# Plan the paid-reader handoff

Prepare access and billing decisions from supplied data. For the full export-import job, use `prepare-substack-import` in this package for field mapping, cleanup, row exceptions, reconciliation and upload batches, then use this skill for access and billing decisions. A paid-reader question alone needs the cohort handoff, not a full cleanup pack. Read selected files if available; screen descriptions establish only what the user describes.

## Deciding rules

Route sources read 2026-10-11: general migration updated 2026-01-22; Ghost updated 2025-01-02; Beehiiv updated 2026-08-03. Exact URLs and scope are in the reference below.

Generic migration: preserve email and expiration/renewal dates. Temporary comps grant access, not imported payment authority; readers later need payment details to continue. Documented durations are 7, 30, 90 days; 6 months; 1 year; forever. A duration menu is not proof that any arbitrary date can be imported.

Ghost exception: its official guide uses the existing Ghost Stripe account. Enable Payments starts a scan, potentially 30 minutes; the confirmation reports eligible subscriptions. Then the native paid import requires revoking Ghost access in Stripe's Installed apps before confirming disconnection. This is a high-responsibility user action, not something to infer from a CSV or execute automatically. Verify the account's actual scan and UI; no eligibility guarantee.

The newer Beehiiv guide establishes free subscriber import but does not establish a paid transfer workflow. Do not extend Ghost's route to other platforms solely because they use Stripe. For other or unclear cases, prepare a comp/re-subscribe fallback and a focused support question about native transfer eligibility. Do not promise that every paid reader must reauthorize if a verified native transfer applies.

Read [the paid-reader references](references/paid-readers.md) before choosing the route. Choose the source-specific route over the general guide only when the user's platform and account evidence match it.

## Build the handoff

1. Establish source platform, move date/time zone, payment state, active versus cancelled/past-due status, consent/suppression, and paid-through or renewal evidence. A cancelled subscriber may still have prepaid access. Never equate cancellation date with access end. Keep ambiguous dates verbatim and hold date-dependent choices until format/time zone is known. A paid flag alone proves neither active billing nor consent.
2. Make mutually exclusive cohorts: eligible native transfer with supplied confirmation; remaining prepaid access; active paid with unresolved transfer; expired/free; held/conflicting evidence. Track original row IDs and suppressed readers separately. Unknown consent prevents email enrollment; handle access/support separately without silently re-subscribing them.
3. When requested or needed to compare cohorts, return a compact table with the relevant source rows, paid-through dates, access, billing and reader actions. Include only columns that help the requested decision. For a comp, compare actual available durations with each promised end date. If exact coverage is unavailable, show the gap or extension and ask the owner to choose; never round down or grant forever by default. Calculate remaining days only from unambiguous dates with the date boundaries and a compact formula; do not enumerate every menu alternative when the user only needs coverage or a gap. Calendar months are not assumed to equal 30 days. Preserve different renewal dates rather than flattening annual readers into one month.
4. Plan old-platform billing alongside the new route. For native Ghost transfer, the documented disconnection step prevents duplicate charges. For a comp fallback, the old billing stop/pause date and scope require owner/provider confirmation before the move; do not cancel or pause automatically. Patreon's one-month pause example is not a universal or permanent billing stop. Verify the applicable Patreon billing model and what resumes after the pause before relying on it; separate approval of longer access from approval of a durable stop to old billing. Do not promise zero duplicate charges from an export.
5. Give a sequenced native handoff with separate confirmation points: verify export and suppression; verify Stripe route/scan if applicable; approve billing cutover; prepare/import consented email cohorts with the welcome-email preference verified (off during staging unless the user chooses otherwise); verify resulting access and billing separately; apply approved comps where needed; draft a migration notice only if requested, using real dates and approved links. Warn if a list-only import leaves a paid cohort without intended access. Use the labels established by the supplied screen; do not add unseen navigation labels. Before Ghost revocation, retain subscription identifiers, cadence and renewal evidence for reconciliation. Keep a non-eligible reader's access choice separate from approval to transfer eligible subscriptions. The user performs account changes and sending.
6. A transfer is complete only with native confirmation and reconciled outcomes, not because the list imported. Missing scan results, unavailable comp durations, unknown dates or unsupported billing routes remain named exceptions. Finish the requested answer first; ask only for the next genuinely blocking decision, without bundling independent approvals.

## Worked example

Fictional company: Amber Quay Letters. Moving from Patreon on 2026-10-14. Two annual members have paid access through 2027-01-14; both opted in. No native transfer confirmation is supplied.

Example output: “Both members: preserve paid access through 2027-01-14; future billing requires a verified new subscription route. Keep those dates out of the email-only upload. A 90-day comp is not the same as three calendar months: remaining days = 2027-01-14 minus 2026-10-14 = 92 days. The published menu does not show an exact 92-day option. Confirm an available access arrangement before import; also confirm how old billing stops so it does not overlap. Which access arrangement do you want if the current screen cannot match January 14?”
