# Prepare the subscriber import

Accept pasted CSV/table text, selected CSV/XLSX/ODS exports, or described screens. If only a sample or screen description is supplied, produce the requested deliverable for those known rows and label its sample scope; do not certify the full list or invent unseen rows. If actual selected files are readable, use available local tools to create the requested files; otherwise provide exact CSV text for the known rows.

## Deciding rules

Current import rules: dedicated list-import guide, updated 2026-08-24 and read 2026-10-11; source URLs and conflict notes are in the reference below.

The current dedicated import page lists CSV, XLSX, and ODS; duplicates are skipped and invalid domains can be skipped. Consent confirmation is required. You can import to the publication or select a specific section; a section-targeted import adds readers only to that section. Imported-list deletion requires a human support request. The older general guide mentions TXT; prefer CSV and do not promise TXT acceptance. No checked source establishes a byte/row maximum, exact required column header, arbitrary custom-field mapping, or a duplicate-based update operation. `email` is our output convention, subject to native preview verification.

This skill owns mapping, cleanup, row exceptions, reconciliation and upload batches for the full export-import job. When paid records appear, also use `plan-paid-reader-migration` in this package for access and billing decisions; keep its cohort decisions alongside this pack.

Temporary paid access is not billing transfer. Preserve renewal/paid-through dates and route paid cohorts to an access/billing handoff. Ghost has a documented Stripe transfer route; do not replace that with a blanket requirement to re-enter payment details. An account-specific screen controls eligibility.

Under review is pending human review, with a 72-hour target that can take longer. Denied is a risk decision; offer voluntary off-platform signup, not repeated uploads or splitting to bypass it. A skipped count alone does not prove which rows failed.

Read [the source register](references/substack-import.md) for support and conflicts before a platform-specific recommendation.

## Build the pack

1. Identify source platform, file coverage/export date, publication or intended section, payments state, welcome-email preference, and suppression/opt-in meaning from supplied evidence. Missing details block only dependent actions. Payment status is not consent evidence.
2. Assign stable source row IDs. Map each source field to **upload email**, **eligibility**, **paid-access handoff**, or **local-only reconciliation**. Names, tags, payment identifiers and dates are not promised as import fields. Preserve the original values privately; do not silently overwrite the export.
3. Use a CSV-aware parser for quoted fields. Trim surrounding email whitespace. Preserve address characters; do not repair domains, strip plus tags/dots, or assume case differences identify one person. Flag case-only variants without holding a separately confirmed exact address solely because a variant exists. If consolidating case variants, state the normalization explicitly and preserve originals; any suppression or conflicting consent still blocks the group. Check blank/malformed addresses; flag suspected domain typos as unconfirmed, not a deliverability verdict.
4. Assign one row disposition: ready, duplicate-of-row, excluded-suppressed, or hold-with-reason. Keep all additional reasons as notes. Exact duplicates collapse only when consent/status agree. Any suppression or conflicting consent blocks the whole address group until resolved. Never restore unsubscribed, complained, or hard-bounced readers through import. Unknown consent stays on hold. Confirmed destination matches are separate from source duplicates; unknown overlap stays unknown. Do not promise existing subscriber access/status will change through re-import.
5. Produce the requested CSVs and exceptions (row ID, reason, proposed action); include mapping only when useful. Name batch files by their actual source row IDs or meaningful cohort, and keep ready email-only batches separated by native import settings such as section or access cohort. Preserve paid metadata in a separate cohort ledger. An eligible paid email may be ready for list import while its access/billing decision remains on hold: state that consequence beside the batch. Reconcile source rows = ready rows + duplicate rows + excluded rows + held rows; readiness is not a forecast of newly added members.
6. Handoff: Subscribers → Add subscribers → upload; check native email recognition, consent, publication/section, subscription type if payments are enabled, and welcome-email setting before the user confirms Import. Recommend leaving welcome mail off during staged migration, unless the user chooses otherwise. After completion, request actual added/skipped/status results and compare them with submitted unique rows and any known destination matches. Wait through review; do not claim completion from a preview. Unexpected skips need supplied row details or support. Lead reconciliation answers with what the totals establish, what remains unknown, and the next lookup or concise support request. A known existing member is a likely duplicate skip, not a confirmed row result. Prepare a retry CSV only after identifying missing eligible addresses; omit already-present readers and hold unconfirmed typos. Do not upload again blindly.

## Worked example

Fictional company: Cedar Lantern Editions. Three source rows, all opt-ins: R1 and R2 contain the same exact free-reader address; R3 is an annual paid reader with paid-through date 2027-04-08. No target-member export is supplied. The user wants no welcome mail.

Example output: “Ready: one free email and one annual-paid reader’s email in separate batches. R2 duplicates R1. Keep R3's paid-through date in the access ledger; decide paid access before uploading that batch. Mapping: email → upload; paid status/date → access handoff; source row ID → local ledger. Counts: 3 source rows = 2 ready + 1 duplicate + 0 excluded + 0 held. New additions remain unknown because destination overlap is unknown. In the preview, verify email recognition and keep welcome mail off.”
