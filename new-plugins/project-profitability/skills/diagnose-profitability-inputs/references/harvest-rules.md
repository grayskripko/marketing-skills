## Interpretation and calculation conventions

The source's “days included” is implemented as inclusive calendar days: end − start + 1. This is an explicit calculation convention, illustrated by the dated examples, not a claim about an undisclosed internal API. If supplied report numbers disagree, show reported − calculated and request the applicable date basis rather than asserting a platform error.

The current report article says tables show entries with time in the viewed period and also describes an unattributed fixed-fee row. Preserve supplied unattributed amounts; do not infer that absence from a table removes revenue from the company total.

The report specifies the larger project invoiced amount but does not explain tax/credit/status/mixed-invoice composition. Require a supplied project-attributed amount rather than invent those semantics. Likewise, expense attribution to teammate/task is not specified by the fee toggle; retain unattributed expense costs when detail is absent.

Package calculation conventions: difference = reported − expected; margin = profit/revenue; a zero revenue denominator is undefined. Compute at full precision; default to supplied report precision for display, but follow an explicit precision request (use exact fractions or repeating decimals for no rounding); explicitly reconcile any remaining cents. These are calculation conventions, not platform policies. No authored forecast, pricing target or arbitrary score is used.

## Budget-alert clarification — checked 2026-10-12

[Budget email alerts](https://support.getharvest.com/hc/en-us/articles/4407283487629-Budget-email-alerts) specifies the configured percentage threshold, which can be below 100%. Alerts are sent the morning after that threshold is exceeded, at 3:00 a.m. Eastern (US). Regular-budget alerts repeat weekly until archiving, disabling alerts or updating the budget removes the overrun; monthly-budget alerts go out once per month. This distinguishes the weekly backfill warning above from monthly-budget behavior.
